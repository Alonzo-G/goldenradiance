# ADR-007: 搜索采用 Pagefind 静态索引 + 自建 SKU 双层前置

## Status

Accepted (2026-10-01)

## Background

设计要求（docs/UIUX.md §2, PRD §3.3 / §8.1）：千级 SKU 的搜索必须同时支持

1. **SKU 精确匹配**（买家已知型号时直达产品页）
2. **模糊容错**
3. **did-you-mean 纠错提示**

同时提出了正当质疑：**静态站能否满足？不行就要上 MeiliSearch / Algolia 或 SSR/ISR。**

结论是静态站可以满足，无需托管检索服务。本 ADR 说明为什么、怎么做，以及它的边界在哪。

## Decision

采用 **Pagefind 1.5.2** 作为全文检索底座，并在其前面加一层**自建的 SKU 索引**做精确匹配与纠错，形成三层递进：

```
用户输入 q
  │
  ├─ L1  SKU 精确匹配            dist/sku-index.json（构建期生成，约 80 KB）
  │      O(1) 查表，命中即直达 PDP，不再往下走
  │
  ├─ L2  SKU 模糊 + did-you-mean  同一份索引
  │      编辑距离 ≤ 2 的最近候选，展示 "Did you mean: FB-2317?"
  │
  └─ L3  Pagefind 全文检索        dist/pagefind/
         L1/L2 无高置信命中时才懒加载，不进首屏
```

### 为什么 L1/L2 必须自己写而不用 Pagefind

Pagefind 是**词法检索**引擎，它的强项是全文相关性排序，而不是「字符串精确/近似匹配」。让买家输入 `FB-2317` 这种型号串去走全文检索，既慢又可能排不到第一。

更重要的是 **did-you-mean**：要做到「你这个型号打错了一位，应该是 FB-2317」，本质是在 SKU 字符串集合上做编辑距离检索。这是几十行代码 + 一份构建期生成的 JSON 就能完成的事，不需要搜索引擎。把编辑距离限制在 ≤ 2 是为了避免 O(n·m) 在千级列表上产生可感知延迟。

### Pagefind 的关键事实（2026-10-01 核实）

- `pagefind@1.5.2` 为 npm latest。
- **按语言建独立索引**：读取 `<html lang>`，为每种语言各建一份索引，浏览器端按当前页面语言加载对应索引。这与 ADR-004 的 hreflang 路径前缀结构天然对齐。
- **CJK 分词**在 **extended release** 中提供，`npx pagefind` 默认使用的就是 extended 版本，因此中文无空格文本可被切分。
- **索引是自己分块的静态文件**，浏览器按需拉取命中的块而非整个索引，初始带宽开销小。这是它相对 Fuse.js（需整份 JSON 进浏览器）的核心优势。

### 已知限制（必须告知 PM 与设计师，验收时不可当作 bug）

1. **对 CJK 不做 stemming（词干还原）**。中文可正确切分，但不会把不同词形归并到同一词根。对本站影响有限（主要受影响的是英文材质词的形变），但必须写进验收标准。
2. **索引只包含公开的构建产出 HTML**，因此索引文件里**不得**含仅供登录用户查看的内容（本站无此类内容，但 v2 需注意）。
3. **索引新鲜度与部署绑定**：内容变更必须重新构建才会反映到搜索结果。
4. **「最后一公里」陷阱**：Pagefind 忠实索引它收到的 HTML。若不做限定，导航栏/页脚/Cookie 提示等每页重复的文案会被全量索引，导致**每个词都命中每个页面**——这是 Pagefind 最常见的沉默降级。

## Consequences

### 正面

- **零后端、零订阅成本**：索引是静态资源，随构建产物发布、随回滚一起回滚。
- **索引与站点版本强一致**：不存在「数据库内容与线上页面不同步」这类经典问题。
- 按需分块下载，对全球分布的买家带宽友好。
- 分语言索引，天然支持 i18n。

### 负面

- 索引新鲜度与部署绑定，无法反映两次构建之间的内容变化（本站可接受，因为内容本来也要走 CI）。
- 无查询分析、无同义词治理、无托管服务的运营面板。这些是放弃了的能力。
- CJK 无词干还原（见上）。
- 需要额外写 `scripts/build-sku-index.mjs` 并接入 CI。

### 必需的硬约束（违反会导致搜索形同失效）

1. 必须用 `data-pagefind-body` **严格限定正文范围**，并用 `exclude_selectors` 排除 nav / header / footer / Cookie 提示。
2. 必须验证这条用例：搜一个只出现在页脚的词，**不应**返回全部 SKU。
3. 每个 layout 的 `<html lang>` 必须真实输出 `en` / `zh`，不能只靠 URL 前缀。
4. 若未来改成客户端语言切换而不重载页面，需调用 `destroy()` 后 `init()`。

### 触发切换到托管检索的条件

以下任一成立时弃用 Pagefind，改用 MeiliSearch / Algolia：

1. 需要**按登录用户差异化**搜索结果（权限感知检索）——索引是公开静态资源，做不到。
2. 需要**实时库存**反映到搜索结果。
3. 需要**查询分析、同义词治理、深度定制相关性**。
4. 需要**语义检索**（向量 / 混合检索）。例如买家搜「上次那个不会掉色的款的同类」这类查询。

Phase 1 上述四条均不成立。

## Alternatives Considered

| 方案 | 否决理由 |
|---|---|
| MeiliSearch / Algolia | 需独立服务与同步作业；MVP 无上述四条需求，过早引入是过度设计 |
| Fuse.js | 需把整份集合 JSON 送进浏览器再内存匹配，千级 SKU 下体积与带宽不及 Pagefind 的分块策略 |
| Lunr.js | 同上，且生态活跃度不及 Pagefind |
| PostgreSQL /database tsvector 全文检索 | 本站未引入 Postgres（见 ADR-006）；且中文分词支持需额外配置 |
| 服务端 SSR / ISR 搜索接口 | 为满足搜索而牺牲全站静态性，与 ADR-001 冲突；本需求静态站已可满足 |
